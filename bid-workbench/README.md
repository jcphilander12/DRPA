# DRPA Bid Workbench

A private shared bid workspace for tender documents, responses, evidence, review decisions, service modelling, TUPE and commissioner FMT completion.

## Start testing

The existing private Site is at https://drpa-bid-workbench.sa33dc.chatgpt.site. It remains restricted to the owner's account. The owner can register members and assignments in **Users and assignments**; each real colleague also needs access through the Site's sharing settings. Registering an email in the app does not send an invitation or change the Site audience.

For a designer's local test on their own computer:

```sh
corepack enable
pnpm install --frozen-lockfile
pnpm typecheck
pnpm build
pnpm test:smoke
pnpm demo
```

Use Node 22.13+ and the package manager version in `package.json`. Open http://127.0.0.1:4180/demo-login. Choose **Test Master**, **Test Writer** or **Test Checker**. Return to that address to switch roles. The demo binds to loopback only, strips incoming identity headers, and uses server-selected test accounts with HttpOnly cookies. It is a local harness, not a production sign-in system. It has synthetic documents, two questions, a staff/TUPE cost model and a small FMT. Its rates and outcomes are fictional. Stop it before deleting `.local-demo` to reset. The managed Sites environment uses its supervised preview instead of this portable server.

This pack contains selected DRPA historical source extracts as well as application code. Treat it as confidential. The local demo replaces the initial workspace with synthetic fixtures; it does not use the historical extracts as test outcomes.

## Roles and assignments

| Operation | Master | Assigned writer | Assigned checker |
| --- | --- | --- | --- |
| Register users and grant/revoke assignments | Yes | No | No |
| View a question or finance section | All | Assigned work | Assigned work |
| Edit a response or model | Yes | Assigned write access | No |
| Add a comment | All | Assigned work | Assigned work |
| Accept/reject and incorporate comments | Yes | Assigned write access | No |
| Record a current-version check | Yes | No | Assigned check access |
| Mark answers, model and FMT complete | Yes | No | No |
| Maintain reusable evidence, publish feeds and restore a backup | Yes | No | No |
| Delete bids/questions/ITT documents; submit, archive or restore a bid | Yes | No | No |
| Read or write post-bid analysis | Yes | No | No |

Assignments cover individual questions and the ITT, briefing, service model/TUPE and FMT sections. Bid writers can read relevant ITT and historical evidence for their assigned bid. Original workforce/finance files and detailed models require a finance assignment; response-only users receive confirmed finance summaries. Membership and permissions are enforced by the server, including direct API and file requests. Inactive accounts cannot use the workbench.

## Working through a bid

1. Create a bid and upload the current documents in **ITT documents**. Review extracted text, mark verified documents and edit the detected question candidates before importing. Existing answers are retained; duplicate references are blocked. This is assisted extraction, not a guarantee that every requirement has been identified.
2. Use **Bid briefing and data** for a source-based summary, detected term/budget/deadline excerpts, required deliverables and suggested information gaps. Assign owners and due dates, then record the supporting information before confirming each item. Detected dates and values require original-document verification. The briefing is generated by local rules; it is not an AI assessment.
3. Keep reusable case studies, selected relevant chat extracts and previous bid material in **Reusable evidence**. Verify facts before approving them for drafting. The app cannot automatically read every ChatGPT chat or a procurement portal.
4. Build the funded delivery plan in **Service model and TUPE**. Enter pathways, staffing and productive capacity, employment assumptions, anonymised TUPE matches and non-pay/mobilisation costs.
5. Upload the current commissioner workbook in **Financial model / FMT**, map the outputs, verify the target cells, validate and export. Complete the service-model approval, reopen/recalculate the exported FMT in Excel, reconcile the summaries, and record the master FMT approval.
6. Assign writers and checkers. Draft each response in **Response studio**, with its exact wording, criteria, word/character limit, counting choices, style, confirmed financial facts and selected experience. Use the ChatGPT companion now, or the direct draft/refine buttons after API activation.
7. Send a first draft for review. Checkers add comments or exact quoted wording suggestions. Writers accept/reject with a decision record. A suggestion is applied only if the reviewed answer/evidence still matches; other accepted comments need an incorporation or verification record.
8. Every assigned checker must check the current version. With no checker assigned, the master performs the check. The master then marks the answer complete. Answer completion requires an approved FMT. Editing the answer, evidence, rules or funded model invalidates affected approvals.
9. Export Word review/submission copies, workspace JSON, model and mapping CSVs, a costed XLSX and a review ZIP containing decision history. Check the final response count in the actual submission portal.

The overall progress bar gives equal weight to each answer plus four bid sections: verified ITT with confirmed submission deadline, confirmed required data, approved service model and approved FMT. Open or accepted-but-unincorporated section comments prevent its completion. Percentages measure these workflow items, not time spent or commissioner scoring.

## Financial model behaviour

- Planned establishment uses entered WTE or weekly coverage converted through full-time hours and productive weeks. All assumptions remain editable; a missing cost is unavailable, not zero.
- Matched included TUPE WTE offsets recruitment. It is not added a second time. Unmatched transfers, excess WTE, duplicate anonymised references and unverified terms block sign-off.
- TUPE basic pay is annual full-time equivalent; allowances and other annual costs are per employee. The importer requires confirmation of pay basis, hours divisor and pension units. It imports selected role/pay/hour fields into new anonymous aliases, not names, date of birth or contact details. The uploaded original remains restricted to the assigned finance team.
- New recruitment is costed from a full-time role assumption. Employer contributions use the entered rate and threshold; pension uses basic pay. This is a planning convention, not a payroll engine. Use checked employment assumptions, and separately account for premiums, agency, overtime, leave and other liabilities where relevant.
- Annual pay escalation, recurring non-pay escalation, mobilisation in Year 1, capital treatment, overhead, margin versus markup, and the entered budget are explicit.
- Each staff WTE/cost and non-pay row must map for every contract year. Non-zero overhead and profit need destinations too. Row suggestions for the Winchester template start unverified; check the exact service, provider, grade and input row yourself.
- The server checks the original workbook fingerprint and actual cells. Formula cells, locked protected cells, merged targets, text targets and duplicate destinations are rejected. It changes mapped numeric inputs and preserves the original workbook package, styles and formulas. Stale formula caches are cleared and recalculation is requested.
- There is no Excel calculation engine. The export must be reopened and recalculated in Excel (or an independently checked compatible application). Final FMT approval requires a review record of the recalculated summaries. The approved costed workbook becomes the source for confirmed bid-writing facts. Model/mapping changes clear those facts and the old approval.

## AI connection

Direct AI is implemented but not connected in the current Site. There is no API key in the pack or deployment. The ChatGPT companion prepares a prompt using the exact question, verified source passages, DRPA rules, confirmed finance facts, criteria and current input; import its structured result or paste/edit the answer.

For the hosted Site, use secure OpenAI Developers API setup with the owner's approval and configure `OPENAI_API_KEY` as a server secret. API usage is billed separately from ChatGPT. `OPENAI_MODEL` is a server setting, currently `gpt-6-astra`. Never put a real key in the browser, source, backup or a chat. The Responses adapter uses structured output and `store:false`; that flag does not establish zero data retention. Provider settings and agreements govern retention.

The 40-started-request daily guard is per member across their assigned bids. An over-limit rewrite can make a second paid call. Failed requests may incur charges. Paid API behaviour and factual answer quality have not been exercised. Human review remains required.

## Designer deployment

This is a server application: React/TypeScript with Vinext/Vite, a Cloudflare Worker, D1 and private R2 storage. Uploading just HTML to ordinary static hosting will not provide authentication, shared data, uploads or permissions.

### Keep the existing Site

Use the existing Site's source workflow and private runtime bindings. `AUTH_MODE=sites` trusts the authenticated identity supplied by its dispatcher. `MASTER_EMAIL` is a server configuration value. The dispatcher may supply email without user ID, so the tested email fallback is retained. The source download removes the original project identifier; obtain the actual identity through the owner's Sites workflow when updating the original.

### Independent Cloudflare deployment

1. Create a Worker, D1 database and private R2 bucket in the chosen account. Protect the entire production hostname with a Cloudflare Access application and the intended staff allowlist before inviting users. Use a protected custom domain and disable an unprotected alternate workers.dev origin.
2. Copy `deployment/wrangler.example.jsonc` to `deployment/wrangler.jsonc`; fill in the database/bucket and Access application values. Keep `AUTH_MODE=cloudflare-access`. Set `MASTER_EMAIL` to the exact authorised master sign-in email. Do not set `LOCAL_DEMO` on production.
3. Run the full build/checks above, then apply all immutable D1 migrations with `pnpm exec wrangler d1 migrations apply DB --remote --config deployment/wrangler.jsonc`. Back up existing data before a migration.
4. Configure any API key with `pnpm exec wrangler secret put OPENAI_API_KEY --config deployment/wrangler.jsonc`, using private secret entry. Deploy using `pnpm exec wrangler deploy --config deployment/wrangler.jsonc`.
5. Verify that unsigned/expired/wrong-audience JWTs and spoofed Sites headers are denied, then test each real role and file-access boundary. `lib/access-auth.ts` verifies the Access JWT signature, issuer, audience and required claims with the team's public signing keys. No fallback to client-supplied email is permitted.
6. The master registers real users and assigns their work. Both the Access gate and application membership are required. Run the acceptance checklist in `TESTING.md` before live tender use.

The example configuration is a deployment template; no independent Cloudflare account has been provisioned. Another host needs equivalent verified authentication and database/object-store adapters. A source backup contains excerpts and answers, not every uploaded original, role table or audit record; export review history and download original files separately for migration.

## Verification and current limits

TypeScript, production build, meaningful Worker/D1/R2 integration tests and cost/workbook/auth tests pass. The server-exported synthetic XLSX was independently read with OpenPyXL to verify numeric values, formula/protection/merge preservation and recalculation flags. The three-role demo seed is checked. Browser visual QA was unavailable in the authoring environment; the designer should complete the supplied checklist. The portable HTTP demo wrapper has been syntax checked and its Worker/data flow tested, but was not browser-tested here.

Limits: 20 active bids, 80 questions per bid, 60 sources, 12 answer versions, 150 staff lines, 250 transfer rows, 150 non-pay lines and 3,500 FMT mappings. Each original upload is at most 15 MB and each source extract at most 120,000 characters. Standard XLSX parsing is bounded to 30 MB expanded total/10 MB per ZIP entry. The shared JSON snapshot is capped at 1.7 MB; original files and collaboration records are separate. Large portfolios need passages and answer versions moved into indexed records/object storage. Scanned PDFs need OCR elsewhere, and original tables/diagrams require review. Unsupported/encrypted/complex workbook structures need a checked manual process.

Recent history shows the last 100 audit events and recent resolved comments, plus all unresolved comments. Backup/restore resets approvals and does not recreate original uploads, user assignments or comment tables. After restoration the master must recheck the evidence, model and files. The app does not submit tenders or validate every real-world claim or commissioner formula.

Official reference for external authentication: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/

## Deadline, lifecycle and review additions

The submission deadline is a separate confirmed field, with a London date/time and source/clarification note. Candidate extraction recognises common UK date formats and requires verification. The overview counts London calendar days and checks the actual cutoff instant; it refreshes each minute. The ITT completion item includes deadline confirmation. Changing/removing a supporting ITT invalidates its confirmation. The master can record the actual portal submission time in London; this records an event and never submits to Atamis.

Dedicated master-only actions delete a question, an ITT document, a reusable source or a bid after exact-reference/name confirmation. General workspace saves cannot remove bids/questions/ITT documents. Question deletion prunes assignments, checks and comments. Bid/file cleanup preserves originals still referenced by reusable evidence or another archive. Archive instead preserves a fixed snapshot of answers, selected evidence, finance model, available documents and review metadata outside the active workspace. Original archive files and snapshots are master-only. Restoring resets approval/facts and removes the archive entry; reassign the work and recheck it. A backup restore explicitly replaces active content after typing RESTORE, with fresh evidence checks; archives remain.

Response Studio has a search, status filter and next/previous buttons within the filtered question set. Staffing import accepts standard XLSX, proposes sheet/header/column mappings, requires a salary/percentage/capacity-basis review and appends selected establishment rows. Missing assumptions remain null, including employer rates and explicit zeros. Full-time hours and paid/productive weeks are visible, editable assumptions. Only role-level selected columns enter the model. Whole staffing view groups roles by service, provides a comparison table and opens each profile for editing.

An externally completed FMT uses mode `completed`. Upload a recalculated, saved XLSX; select and verify aggregate staffing/financial summary cells; validate and export an exact copy. The server reads actual values (including saved formula values), rejects blank/error/invalid cells and verifies the original fingerprint. Model calculation and internal model approval are not prerequisites in this mode. Final FMT approval still requires a current check, export and master recalculation/financial-summary attestation. Only the selected actual workbook facts enter answers. This is a review workflow, not an Excel calculation engine.

Private post-bid analysis is stored separately from public/shared workspace data and answer packs. Master-only APIs include active and archived bids, saved activity counts, contribution attribution, comment decisions, review waits, reopened work, recorded submission timing, structured delays, constructive feedback and improvement actions. It does not infer hours worked or writing quality. Earlier/offline activity can be unrecorded and needs team context. Feedback is not emailed or shared automatically. Private-review saves have their own revision conflict guard and can be exported separately.

## Governed DRPA Intelligence bridge

The existing Intelligence Site now exposes `/bid-evidence` for the configured master and a separate read-only `/api/bid-evidence` service endpoint. The master selects metric definitions, sites and month range, records aggregate-data/definition review and publishes the scope. Only DRPA approved records with finite usable counts, source references and denominator where required enter the feed. Synthetic/sample records, other tenants, pending submissions, restricted finance metrics and individual notes/details are excluded. Up to 40 records per scope avoids silently truncating the feed; narrow the scope if necessary.

Production server settings:

| Application | Configuration |
| --- | --- |
| Intelligence | `BID_FEED_MASTER_EMAIL`; secret `BID_FEED_KEY` |
| Bid Workbench | `INTELLIGENCE_FEED_URL` (exact HTTPS endpoint); matching secret `INTELLIGENCE_FEED_KEY`; secret `INTELLIGENCE_SITES_TOKEN` for this owner-private Site's service access |

These server settings are configured for the existing private Sites. The feed starts unpublished; no fictional claims are activated. In **Reusable evidence**, the master synchronises a published scope. New/changed extracts start master-only and unverified, carrying site, period, numerator/denominator, source, definition and observation versions. Approval and **Available to assigned team members** are separate choices. Withdrawn/unpublished records lose approval and become master-only. Archives retain their original evidence snapshots. Unchanged records retain the same IDs/retrieval timestamp. Failed, redirected, oversized or invalid feed responses do not mutate the workspace or forward credentials to another location. Refresh is on-demand, not a scheduled job.

Completed response packs/workbooks can be uploaded to reusable evidence against an active or archived originating bid. Originals and extracts start master-only. ZIP files are catalogue entries and cannot be approved as outcome evidence; import a checked individual document/extract instead. Prior bid promises require actual delivery verification.

For another host, supply an equivalent trusted server identity boundary for Intelligence, retain its master guard and configure a new read-only feed secret. Do not publish its existing role-preview application publicly as a multi-tenant production platform. The Bid Workbench independent-host adapter remains Cloudflare Access JWT verification. Keep service credentials out of browser code, exported backups and designer packs.

New verification commands after build: `node scripts/lifecycle-smoke.mjs`, `node scripts/evidence-sync-smoke.mjs`; both are included in `pnpm test:smoke`. The Intelligence source has `node scripts/bid-feed-smoke.mjs` and `node scripts/verify-domain.mjs`. Tests use synthetic isolated databases/buckets and mocked private feed transport. Browser layouts and real Excel workbooks still require owner/designer acceptance.
